Great. For your app, I’d design the backend around this rule:

> **Cloud SQL stores meeting metadata, transcripts, notes, edits, and revisions. Cloud Storage stores audio files. The browser keeps a temporary local draft, then syncs to the backend.**

Use **Cloud SQL for PostgreSQL** rather than MySQL because your app benefits from relational data, JSON document storage, versioning, full-text search, and clean transaction semantics. Cloud SQL for PostgreSQL is Google’s fully managed PostgreSQL database service, so it is a good fit for durable meeting-note data without managing your own database server. ([Google Cloud Documentation][1])

# Core backend decision

Do **not** treat the transcript as the editable note.

Use two separate concepts:

```text
Transcript = what the AI heard.
Note document = what the user edits.
```

That gives you flexibility:

```text
Raw transcript:
  append-only-ish, segmented, timestamped, recoverable

Editable note:
  Notion-style document users can edit, summarize, clean up, and restructure
```

For MVP, you can still let users correct transcript paragraphs, but keep the original machine transcript.

# MVP edit model

For the first version, I recommend a **single-user optimistic edit model**, not collaborative editing.

That means:

```text
User opens meeting note.
Backend returns document content + version number.
User edits locally.
Frontend autosaves every 1–2 seconds.
PATCH request includes expected version.
Backend saves only if version still matches.
Backend increments version.
If version is stale, return 409 conflict.
```

This is much easier than real-time collaborative editing and still feels good for a basic Notion-style editor.

Later, if you want Google Docs/Notion-style live multi-user editing, add Yjs or another CRDT layer. Do not build that for the MVP.

# Data model

## 1. `users`

You can use your auth provider’s user ID as the primary key.

```sql
CREATE TABLE users (
  id TEXT PRIMARY KEY,
  email TEXT UNIQUE,
  name TEXT,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  updated_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

If you use Clerk, Firebase Auth, Auth0, or Supabase Auth, store their user ID here.

---

## 2. `meetings`

This is the parent record for everything.

```sql
CREATE TABLE meetings (
  id TEXT PRIMARY KEY,
  owner_user_id TEXT NOT NULL REFERENCES users(id),

  title TEXT NOT NULL DEFAULT 'Untitled meeting',
  status TEXT NOT NULL DEFAULT 'draft',

  recording_mode TEXT NOT NULL DEFAULT 'microphone_only',

  started_at TIMESTAMPTZ,
  ended_at TIMESTAMPTZ,
  duration_seconds INTEGER,

  transcript_status TEXT NOT NULL DEFAULT 'not_started',
  audio_status TEXT NOT NULL DEFAULT 'not_uploaded',

  created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  updated_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  deleted_at TIMESTAMPTZ,

  CONSTRAINT meetings_status_check CHECK (
    status IN ('draft', 'recording', 'processing', 'saved', 'failed', 'deleted')
  ),

  CONSTRAINT transcript_status_check CHECK (
    transcript_status IN ('not_started', 'live', 'partial', 'complete', 'failed')
  ),

  CONSTRAINT audio_status_check CHECK (
    audio_status IN ('not_uploaded', 'uploading', 'uploaded', 'failed')
  )
);

CREATE INDEX meetings_owner_created_idx
ON meetings(owner_user_id, created_at DESC);

CREATE INDEX meetings_owner_status_idx
ON meetings(owner_user_id, status);
```

Meeting statuses:

```text
draft       = created but not recording yet
recording   = active meeting
processing  = finalizing transcript/audio
saved       = complete and viewable
failed      = error state
deleted     = soft deleted
```

---

## 3. `transcript_segments`

Store transcript as ordered segments.

```sql
CREATE TABLE transcript_segments (
  id TEXT PRIMARY KEY,
  meeting_id TEXT NOT NULL REFERENCES meetings(id) ON DELETE CASCADE,

  provider_item_id TEXT,
  sequence_index INTEGER NOT NULL,

  start_ms INTEGER,
  end_ms INTEGER,

  raw_text TEXT NOT NULL,
  edited_text TEXT,

  is_final BOOLEAN NOT NULL DEFAULT true,

  created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  updated_at TIMESTAMPTZ NOT NULL DEFAULT now(),

  UNIQUE(meeting_id, sequence_index)
);

CREATE INDEX transcript_segments_meeting_order_idx
ON transcript_segments(meeting_id, sequence_index);

CREATE INDEX transcript_segments_provider_idx
ON transcript_segments(meeting_id, provider_item_id);
```

Display text should be:

```sql
COALESCE(edited_text, raw_text)
```

That lets the user correct a transcript paragraph without losing the original AI output.

---

## 4. `note_documents`

This stores the editable Notion-style note.

For MVP, store the editor state as JSON plus a plain-text copy for search.

```sql
CREATE TABLE note_documents (
  id TEXT PRIMARY KEY,
  meeting_id TEXT NOT NULL UNIQUE REFERENCES meetings(id) ON DELETE CASCADE,

  content_json JSONB NOT NULL,
  content_text TEXT NOT NULL DEFAULT '',

  version INTEGER NOT NULL DEFAULT 1,

  last_edited_by TEXT REFERENCES users(id),
  last_edited_at TIMESTAMPTZ,

  created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  updated_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE INDEX note_documents_meeting_idx
ON note_documents(meeting_id);

CREATE INDEX note_documents_content_search_idx
ON note_documents
USING GIN (to_tsvector('english', content_text));
```

Your editor can be TipTap, Lexical, Plate, or ProseMirror. The backend should not care. It only stores:

```ts
type NoteDocument = {
  type: "doc";
  content: Array<unknown>;
};
```

The important fields are:

```text
content_json = rich editor document
content_text = searchable plain text
version      = optimistic locking version
```

---

## 5. `note_revisions`

This gives you basic edit history.

```sql
CREATE TABLE note_revisions (
  id TEXT PRIMARY KEY,
  note_document_id TEXT NOT NULL REFERENCES note_documents(id) ON DELETE CASCADE,

  version INTEGER NOT NULL,
  content_json JSONB NOT NULL,
  content_text TEXT NOT NULL DEFAULT '',

  edited_by TEXT REFERENCES users(id),
  change_source TEXT NOT NULL DEFAULT 'user',

  created_at TIMESTAMPTZ NOT NULL DEFAULT now(),

  UNIQUE(note_document_id, version)
);

CREATE INDEX note_revisions_document_version_idx
ON note_revisions(note_document_id, version DESC);
```

For MVP, you do not need to save a revision on every keystroke. Save one when:

```text
- meeting is first created
- recording stops
- user edits after a meaningful delay
- user clicks explicit save
- AI summary/action items are generated
```

A practical rule:

```text
Autosave current document every 1–2 seconds.
Create a revision snapshot every 30–60 seconds of editing.
```

---

## 6. `audio_assets`

Do not store audio blobs in Cloud SQL. Store them in Cloud Storage and save metadata in SQL.

```sql
CREATE TABLE audio_assets (
  id TEXT PRIMARY KEY,
  meeting_id TEXT NOT NULL UNIQUE REFERENCES meetings(id) ON DELETE CASCADE,

  bucket_name TEXT NOT NULL,
  object_path TEXT NOT NULL,

  mime_type TEXT,
  size_bytes BIGINT,
  duration_seconds INTEGER,

  upload_status TEXT NOT NULL DEFAULT 'pending',

  created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  updated_at TIMESTAMPTZ NOT NULL DEFAULT now(),

  CONSTRAINT audio_upload_status_check CHECK (
    upload_status IN ('pending', 'uploaded', 'failed', 'deleted')
  )
);

CREATE INDEX audio_assets_meeting_idx
ON audio_assets(meeting_id);
```

For audio upload/download, your backend should issue short-lived Cloud Storage signed URLs. Google’s Cloud Storage docs describe signed URLs as time-limited URLs that grant access to a specific Cloud Storage resource, and they can be used for application-controlled upload/download flows. ([Google Cloud Documentation][3])

# Transcript sync APIs

## Append transcript segments

Do not write every live delta to Cloud SQL. Batch final or near-final transcript segments.

```http
POST /api/meetings/:meetingId/transcript-segments/batch
```

Request:

```json
{
  "segments": [
    {
      "id": "seg_001",
      "providerItemId": "item_abc",
      "sequenceIndex": 0,
      "startMs": 0,
      "endMs": 5200,
      "rawText": "Hello, this is a test meeting.",
      "isFinal": true
    },
    {
      "id": "seg_002",
      "providerItemId": "item_def",
      "sequenceIndex": 1,
      "startMs": 5200,
      "endMs": 9400,
      "rawText": "We are testing the live transcript feature.",
      "isFinal": true
    }
  ]
}
```

Backend behavior:

```text
Upsert by meeting_id + sequence_index.
Do not create duplicate transcript rows.
Do not overwrite edited_text.
```

Example SQL shape:

```sql
INSERT INTO transcript_segments (
  id,
  meeting_id,
  provider_item_id,
  sequence_index,
  start_ms,
  end_ms,
  raw_text,
  is_final
)
VALUES (...)
ON CONFLICT (meeting_id, sequence_index)
DO UPDATE SET
  provider_item_id = EXCLUDED.provider_item_id,
  start_ms = EXCLUDED.start_ms,
  end_ms = EXCLUDED.end_ms,
  raw_text = EXCLUDED.raw_text,
  is_final = EXCLUDED.is_final,
  updated_at = now();
```

Use this while recording:

```text
Browser receives transcript segment.
Browser stores segment locally.
Every 3–5 seconds, browser sends finalized segments to backend.
On stop, browser sends remaining segments.
```

## Update note document

```http
PATCH /api/meetings/:meetingId/note-document
```

Request:

```json
{
  "expectedVersion": 12,
  "contentJson": {
    "type": "doc",
    "content": []
  },
  "contentText": "Customer Interview\nSummary..."
}
```

Backend logic:

```sql
UPDATE note_documents
SET
  content_json = $contentJson,
  content_text = $contentText,
  version = version + 1,
  last_edited_by = $currentUserId,
  last_edited_at = now(),
  updated_at = now()
WHERE meeting_id = $meetingId
  AND version = $expectedVersion
RETURNING id, version;
```

If one row is updated:

```json
{
  "status": "saved",
  "version": 13
}
```

If zero rows are updated:

```http
409 Conflict
```

Response:

```json
{
  "error": "version_conflict",
  "message": "This note changed elsewhere. Reload the latest version before saving.",
  "latestVersion": 14
}
```

This gives you safe editing without complex collaborative infrastructure.

# Autosave behavior

Frontend autosave should work like this:

```text
User edits note
↓
Wait 1000–2000ms debounce
↓
PATCH note document with expectedVersion
↓
If success:
  update local version
  show "Saved"
↓
If 409:
  pause autosave
  show conflict warning
  offer reload / keep local copy
```

UI states:

```text
Saving...
Saved
Offline draft saved
Could not save
Version conflict
```

For MVP, this is enough.

# OpenAI realtime backend endpoint

Keep your normal OpenAI API key only on the server. OpenAI’s Realtime WebRTC docs describe the pattern where the browser asks your server for a client secret or ephemeral token, and your backend uses the standard API key to create it; the docs also state that standard API keys should be used on the server, not in the browser. ([OpenAI Developers][4])

Use:

```http
POST /api/realtime/session
```

Request:

```json
{
  "meetingId": "mtg_01HX..."
}
```

Backend behavior:

```text
1. Authenticate user.
2. Verify user owns meeting.
3. Check user quota.
4. Create OpenAI realtime session/client secret.
5. Store usage/session metadata if needed.
6. Return ephemeral session data to browser.
```

Also set a privacy-preserving user identifier server-side, for example a hash of your application user ID. OpenAI’s docs describe setting `OpenAI-Safety-Identifier` from the trusted backend, not the browser, when creating the realtime session/client secret. ([OpenAI Developers][4])

# Security and access control

Minimum rules:

```text

- Every meeting query is scoped by owner_user_id.
- Never trust meetingId alone.
- Do not expose Cloud Storage bucket publicly.
```

# The most important backend rule

Keep the meeting record recoverable even if one part fails.

```text
If OpenAI fails:
  meeting still saves
  audio still uploads
  transcript status = partial or failed

If audio upload fails:
  transcript/note still saves
  audio status = failed
  user can retry upload

If note autosave fails:
  local draft remains in browser
  backend version is unchanged

If transcript sync fails:
  browser queues segments and retries
```

That gives you a reliable product even before you add advanced AI features.

# Best MVP design

Use this as your implementation target:

```text
Cloud Run API
  Authenticated REST backend

Cloud SQL PostgreSQL
  meetings
  transcript_segments
  note_documents
  note_revisions
  audio_assets

Cloud Storage
  audio.webm files

Edit feature
  JSON document editor
  autosave every 1–2 seconds
  optimistic version locking
  409 conflict handling

Transcript
  segment-based
  raw_text preserved
  edited_text for user corrections

Audio
  direct browser upload using signed URL
  SQL stores metadata only
```

This gives you a clean Notion-style backend: every meeting becomes a durable, editable cloud note, while preserving the raw transcript and audio backup.
